# Multi-Task Fine-Tuning

Phase 14 adds supervised multi-task fine-tuning infrastructure for tokenised
market microstructure sequences. It is designed to test whether a shared
transformer representation can support multiple leakage-safe short-horizon
market-state forecasting heads. It is not an execution system and does not
claim tradability or trading performance.

## Design

`MultiTaskTransformer` reuses the Phase 12 `MarketTransformerEncoder` as a
shared backbone. The encoder consumes the Phase 11 field-wise token tensors:
`event_type`, `side`, `price_bucket`, `quantity_bucket`, `time_delta_bucket`,
`context_bucket`, `source` and `attention_mask`.

The pooled transformer representation is passed to one linear classification
head per supervised task. Phase 14 intentionally supports classification only.
Binary tasks are represented as two-class cross-entropy heads rather than
regression heads.

Supported task categories are:

- mid-price direction;
- return quantile;
- volatility regime;
- spread widening;
- passive fill-proxy;
- adverse-selection proxy.

## Label Alignment

For every token window, the prediction origin is the token window end position.
If a window ends at token record index `t`, the dataset looks for labels whose
origin is exactly `t`, the corresponding source-record index, the source
sequence id, or the exact timestamp key. Timestamp matching is exact. Labels
from future origins are not used.

Labels are generated before dataset construction. Tokenisation never consumes
label values, and the token fields contain only categorical event information
available at or before the window end. This preserves the forecasting-versus-
tradability separation and keeps the label-generation assumptions auditable.

## Missing Labels

Missing task labels are represented with each task's `ignore_index` and a
per-task boolean `target_mask`. Samples with no valid task label are dropped by
default because they cannot contribute a supervised objective. Partially
missing samples are kept, and tasks with no valid labels in a batch are skipped
for the loss. A batch with no valid labels for any configured task raises a
clear error.

## SSL Compatibility

The multi-task model shares the same encoder class as the Phase 13 SSL wrapper.
`copy_encoder_weights_from_ssl` can copy compatible in-memory encoder weights
from a `MarketSSLTransformer` into a `MultiTaskTransformer`. It checks keys and
tensor shapes before loading. Checkpoint loading and persistence are deferred.

## Smoke Runner

`run_multitask_smoke_from_event_log` tokenises a local synthetic canonical
event-log fixture, builds token windows, constructs supervised targets from the
existing label pipeline where practical, and uses a deterministic volatility
regime mapping for the smoke path. It then trains a tiny CPU model for one
epoch by default.

The smoke losses and accuracies are synthetic diagnostics only. They
are not benchmark results, market evidence, cost-adjusted signal quality or
execution-aware validation.

## Leakage Controls

- Token windows use only records at or before the window end.
- Label alignment uses the window end as the prediction timestamp.
- Label values are not included in token fields.
- No random time-series split is introduced.
- The dataset accepts externally generated integer labels and does not fit class
  mappings on validation or test data.
- Future information may appear only in labels generated by the label pipeline,
  not in model inputs.

## Out of Scope

Phase 14 does not implement calibration, Brier score, expected calibration
error, reliability diagrams, confidence filtering, abstention, execution
simulation, backtesting, latency sensitivity, queue-position modelling,
attention analysis, dashboards, live ingestion, or real benchmark reporting.

Calibration and uncertainty analysis are intentionally left for Phase 15.

## Limitations

The current smoke path is intentionally tiny and synthetic. It validates
tensor shapes, loss computation, missing-label handling and CPU
training only. It does not estimate performance under regime shift, fees,
latency, market impact, partial fills or venue rules. Any future reported
result must come from a reproducible experiment artefact with documented
temporal splits and leakage checks.
